# 推荐页交互改造 + 配料精确化 实施方案

## Context（背景与目标）

「融酒」是纯静态本地网页调酒 App（双击 `index.html` 即用，数据存浏览器 localStorage）。用户在使用中提出 4 个问题，本方案一次解决：

1. **返回丢滚动位置**：在推荐页第 2 屏底部点开一张卡片、加入酒柜后返回，页码能回到原处（上一轮已修），但**滚动条回到顶部**，不是原来浏览到的位置。
2. **不要页码翻页**：删掉「上一页 / 页码 / 下一页」，改成**滑到底自动加载更多** + 一个**「换一批」刷新按钮**；同一列表内**不得出现重复配方**。
3. **搜索要「有一个字就能筛」**：多个字不要求连续，**输入里任意一个字命中即保留**（如「莫托」能找到「莫吉托」）。
4. **配料不详细**：全量 1395 条酒谱的配料，改成中国人能直接照做的**公制中文用量**（如 `金酒（60 毫升；原 2 oz）`），原文保留在括号里对照；不确定的行业换算值上网核实。

目标：改完仍满足既有的分层约束（`core` 纯逻辑可单测、`ui` 纯字符串渲染、`app` 装配），`node --test` 全绿，并在真实浏览器（`file://`）下走通验收。

---

## 一、返回时恢复滚动位置（问题 1）

**根因**：`js/app.js` 的 `onHashChange()`（约 L266-279）在 `render()` 之后**无条件**执行 `view().scrollTop = 0`；进详情再返回也走这条路径，于是位置被清零。

**改动（`js/app.js`）**
- `state` 新增两个字段：`scrollMemo`（离开推荐页瞬间的 `view().scrollTop`）、`restoreScroll`（下次渲染是否要恢复）。
- `handleAction('open')`：仅当当前在推荐页时，记 `scrollMemo = view().scrollTop`、`restoreScroll = true`，再 `navigate('#/drink/'+id)`。
- `onHashChange()`：回到推荐页时，若 `restoreScroll` 为真**且筛选未变**，保留 `state.shown` 并恢复 `scrollTop = scrollMemo`（消费后清标志）；其余情况一律 `scrollTop = 0`。
- 「加入酒柜」（`case 'toggle'`）**逻辑不动**——它只重渲染详情页，`back()` 后由上面的恢复逻辑生效。

**保留的既有行为**：detail / cabinet / box 渲染后仍回到顶部。

## 二、去掉页码翻页 → 触底加载 + 换一批（问题 2）

### 2.1 状态改造（`js/app.js`）

- 删除 `state.page`；新增：
  - `shown`：当前已加载条数（初值 `PAGE_SIZE = 30`，语义从「页码」变「已加载条数」）。
  - `lastTotal`：上次渲染时过滤后的总数，供触底判断与底部文案使用。
  - `scrollArmed`：触底检测的「已武装」标志，防止一次滑动连续追加多批。
- **列表不缓存数组**，只存 `shown`，渲染时 `filteredList().slice(0, shown)`。理由：
  - `filteredList()` 在「seed + 筛选 + 配方库」不变时是**确定性**的（同序数组），切片天然是同一序列的前缀 → **不可能重复、不可能漏**，直接满足「不能刷到重复的」。
  - 无需为 seed / 4 个筛选 / 自制增删 / 导入 / 清空写缓存失效逻辑。
  - 需在 `filteredList()` 上方补注释，明确「必须确定性」这一契约。

### 2.2 渲染改造

- `js/app.js`：`recommendParts()` 改为按 `shown` 切片，返回 `{total, shown, listBox, footer}`；`renderRecommend()` 不再写 `state.page`，**也不得**在这里设置 `scrollTop`（追加时必须保持当前位置）。
- `js/ui.js`：
  - **删除** `pageWindow()` 与 `pagerHtml()`（并从导出表里移除；grep 确认无测试引用）。
  - **新增** `listFooterHtml(shown, total)`：输出固定 `id="listMore"` + `data-shown` / `data-total`，未到底显示「已显示 N / M」+「加载更多」按钮（`data-act="loadMore"`）；到底显示「已到底 · 共 M 款」+「换一批」按钮（`data-act="refreshList"`）；空结果返回 `''`（空状态仍由 `emptyHtml` 承担）。
  - `filterBarHtml()`：搜索框外面包一层 `.search-row`，右侧加一个 `.icon-btn` 的「换一批」按钮（`data-act="refreshList"`，title/aria-label「换一批」）。**必须原样保留 `id="searchInput"` 与 `value="..."`**（`phase5/phase6` 有断言）。签名不变。
- `css/style.css`：删除 `.pager / .pg / .pager-hint` 整块（约 L249-260），新增 `.search-row / .list-more / .list-end / .more-btn` 样式。

### 2.3 触底加载（`js/app.js`）

- 滚动容器是 `#view`（`.phone` 是 `overflow:hidden`，`window` 收不到滚动事件），在 `bindEvents()` 里对 `#view` 绑一次 `scroll`（`{passive:true}`）；`#view` 元素本身在渲染间不被替换，无需重绑。
- `onViewScroll()`：
  - 非推荐页 / 无布局尺寸（`clientHeight`、`scrollHeight` 为 0，含假 DOM）→ 直接返回。
  - 距底 < `BOTTOM_THRESHOLD = 240`（约 2 张卡片）：若 `scrollArmed` 且 `shown < lastTotal`，则 `shown += 30`、`scrollArmed = false`、`renderRecommend()`（不碰 `scrollTop`）。
  - 离开触底区（继续下滚或内容变长）→ `scrollArmed = true` 重新武装。
  - **不用定时器防抖**：假 DOM 的 `win.setTimeout` 是永不回调的空桩。
- 新动作：
  - `case 'loadMore'`：同触底追加逻辑（给「加载更多」按钮用，也为不便于滚动的环境兜底）。
  - `case 'refreshList'`（换一批）：`state.seed = 新随机数`、`shown = 30`、清 `restoreScroll/scrollMemo`、`renderRecommend()`、`scrollTop = 0`、`scrollArmed = true`。**不清筛选**（只换顺序）。为可测试，加 `deps.random` 注入点（默认 `Math.random`）。
- `state.shown` 复位为 30 且回到顶部的位置：搜索输入、`fTaste/fIng/fStr/clearFilter`、`saveRecipe`、`delCustom`、`applyImport`、`clearAll`、切到 cabinet/box tab。
- `syncHash()` 去掉 `page` 一项（`core.parseHash/buildHash` 无需改动；旧的 `?page=` 参数会被忽略）。
- `filteredList()` 里对 `custom.concat(...)` 结果补一次**按 id 去重**（2 行），防止脏备份导入产生的重复 id。

## 三、搜索改为逐字匹配（问题 3）

`js/core.js`：
- 新增并导出 `queryTokens(q)`：去空白、转小写；**纯 ASCII 片段整段作为 1 个 token**（否则 `mojito` 会被拆成 `m/o/j/...` 命中全库），**含中文的片段逐字拆**；去重。
- 重写 `matchesQuery(drink, q)`：token 之间是 **OR**（任意一个命中即保留）；匹配范围沿用现有 haystack（`name / name_zh / name_display / category / glass / ingredients_zh / ingredients_en`）。
- `filterRecipes(list, filters, tagsApi)` **签名与语义不变**（仍委托 `matchesQuery`），因此 `buildBlindPool` 等调用方自动跟随。
- 性能：实测 `filterRecipes(q)` ≈ 2 ms/次（1395 条），**不加 debounce**。

**必要配套**（否则 OR 太吵，实测「莫吉托」会命中 118 条）：
- `js/app.js` 的 `filteredList()` 末尾，当 `state.q` 非空时按**命中 token 数降序**做**稳定**排序（同分保持洗牌序），排在切片之前。约 15 行，复用 `core.queryTokens`。
- 搜索框 placeholder 改成能说明语义的文案（如「任一字命中，输入越少结果越多」）。

**必读副作用**：`onHashChange()` 需要一个**幂等跳过**——若解析出的 route 与筛选和当前 state 完全一致，直接 `return`，不重渲染。原因：`file://` 下 `history.replaceState` 会抛 `SecurityError`，`syncHash()` 退回 `location.hash = ...`，会异步回响一次 `hashchange`；若回响时重渲染，正在输入的搜索框会被销毁、焦点与软键盘丢失，**逐字搜索将无法使用**。（实现时在浏览器 console 确认本机属于哪条路径。）

## 四、配料用量精确化（问题 4）

### 4.1 现状（实测）
- 源数据 `素材/index.zh.json`（单行压缩 JSON，1.25 MB，字段见 §5）中 `ingredients_zh` 共 **6345 行**。
- 分桶：中文+数字+已知单位 **2669**；中文+数字但单位不认识 **223**；含拉丁字母（英文单位 / 英文说明）**2404**；无数字无拉丁 **1049**（多为「鲜榨柠檬汁」这类无用量行）。
- 单位出现量级（`ingredients_en` 侧）：oz 1637、cup 640、ml 423、cl 262、tsp 227、part 173、dash 165、shot 162、cube 142、slice 130、leaves 77、wedge 49、glass 47、tbsp 45、twist 38、bottle 42、can 36、to taste 35、pinch 34、splash 30、drops 25、sprig 24、scoop 20。

### 4.2 做法：新增换算脚本 `tools/normalize-units.js`

- 读 `素材/index.zh.json` → 逐条改写 `ingredients_zh` → 原格式（单行压缩）写回；`--dry` 只打印报告不写文件。
- **输出格式**：`材料名（公制用量；原 原文档）`
  - 例：`淡朗姆酒（60–90 毫升；原 2-3 oz）`、`糖（10 毫升；原 2 tsp）`、`安高天娜苦精（1.2 毫升；原 2 dashes）`、`方糖（1 块，约 4 克）`、`苏打水（适量）`。
  - 原本已是公制中文化的行：统一为 `材料名（30 毫升）`，**不写「原」**。
- **换算表**（已知定值直接算；`dash/splash/shot/part/pinch/scoop/glass/twist` 等含糊值**上网核实**后在 PRO.md 附来源）：

  | 原文 | 公制 | 备注 |
  | --- | --- | --- |
  | oz / 盎司 / 液盎司 | 30 毫升 | 29.57，按调酒惯例取 30 |
  | cl / 厘升 | 10 毫升 | 定值 |
  | tsp / 茶匙 | 5 毫升 | 4.93 |
  | tbsp / tblsp / 汤匙 | 15 毫升 | 14.79 |
  | shot / jigger | 45 毫升 | 1.5 oz |
  | cup | 240 毫升 | |
  | dash | 约 0.6 毫升 | 1/8 tsp |
  | splash | 约 5 毫升 | |
  | pinch | 约 0.3 克 | 一小撮 |
  | drop | 1 滴 | |
  | cube | 1 块（约 4 克） | 方糖 |
  | slice / wedge / leaves / sprig / twist | 片 / 块 / 片 / 小枝 / 条 | 计数量词 |
  | scoop | 1 大勺（约 15 克） | |
  | glass / bottle / can | 杯 / 瓶 / 罐 | 含糊值标「约」 |
  | part | 份 | 相对比例，**不换算数值** |
  | to taste | 按个人口味 | |
  | Fill to top | 加至满杯 | |

- **数字解析**：支持整数、小数、分数（`1/2`→0.5）、带整数分数（`1 1/2`→1.5）、区间（`2-3` / `2–3` / `2 to 3`→`60–90 毫升`）。
- **取整规则**：≥10 毫升取整到 5 毫升；<10 毫升保留 1 位小数。
- **保守原则**：规则无法有把握解析的行**原样保留**，不硬改；无任何用量的行统一补 `（适量）`。
- **幂等**：已含「毫升/克/滴/个…」且无「原」的行直接跳过，重复执行不会二次换算。
- **报告**：打印各规则命中数、跳过数、无法识别的行数与前若干条样例，便于人工抽查。

### 4.3 配套
- 重新生成 `js/data.js`：`node tools/gen-data.js`（含 1395 数量守卫）。
- `js/ui.js` 的 `aboutHtml()`（约 L245-251）删掉「用量单位保留原文，未做统一换算」这句，改为说明已换成公制中文（原文保留在括号内）。
- `PRO.md`：新增「配料换算表」小节 + 变更记录。

## 六、验收

**自动测试**：`node --test "tests/*.test.js"` 全绿（当前 90，改造后约 95+）。
覆盖的关键不变式：
- 追加后总数为 60、`new Set(ids).size === 60`（无重复）、前 30 条顺序不变；
- 触底追加一次；仍在底部且未重新武装时不重复追加；离开触底区后可再次追加；
- 结果集不足 30 时 `shown` 不溢出、显示「已到底」；
- 换一批后回到 30 条、`scrollTop = 0`、顺序变化；
- **返回恢复滚动**：滚到 4200 → 进详情（滚 0）→ 加酒柜 → 返回后 `shown` 与 `scrollTop` 都回到原值；
- 搜索 `'莫托'` 命中「莫吉托」、`'莫'` 结果数 < `'莫吉托'`、无意义串 0 条。

**浏览器实机（`file://` 双击 `index.html`）**：
1. 逐字输入「莫托」不丢焦点（验证 `onHashChange` 幂等跳过）；
2. 滑到底自动追加、无重复卡片、不会一次跳多批；
3. 滚到第 2 屏下方 → 进详情 → 加入酒柜 → 返回，位置与条数保持；
4. 点「换一批」回顶且顺序变化；
5. 打开任一条含 `oz/tsp/dash` 的酒详情，核对配料已是「公制；原 …」双写。

> 浏览器验证需临时起本地静态服务（`file://` 不能用浏览器工具导航），验证完删除临时文件。

## 八、风险与取舍

1. **逐字 OR 会显著放宽结果集**（实测「莫吉托」→118 条，4 字查询近乎全库）。已用「按命中字数降序稳定排序 + 显示真实命中数」缓解；**不做停用字表**（会破坏已确认的口径）。若仍嫌吵，后续可改成「每个字都要出现（不要求连续）」。
2. **`file://` 下的回响 hashchange** 会销毁输入框——已用幂等跳过修掉；这是逐字搜索能用的前提。
3. **追加时整页重渲染**（约 14 ms，实测可接受）：会重置筛选条横向滚动位置；不做增量 DOM，因为假 DOM 无法建模且会让现有断言失真。
4. **滚动位置只在内存**：在详情页刷新后再返回会退回顶部（取舍，不写进 URL）；酒柜页本次不记忆滚动位置。
5. **配料脚本不可能 100% 无误**：采用保守规则 + 未识别行原样保留 + 报告人工抽查；换算表写进 PRO.md 备查。`instructions_zh` 里的用量表述本次不改。
